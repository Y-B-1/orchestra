# Research: PR review, skills, and agent orchestration (expires: end of current sprint)

## Question

How Cursor custom subagents and Agent Skills load; when skills or subagents are appropriate; what CodeRabbit, Graphite Diamond/AI Reviews, GitHub Copilot code review, and Cursor Bugbot publicly claim; how node-based agent builders compare with Orchestra's typed JSON routing graph; and which August 2026 Cursor model-pool facts and prices are publicly documented.

## Findings

### 1. Cursor primitives

- A project custom subagent is a Markdown file in `.cursor/agents/` (or compatible project locations), with frontmatter such as `name`, `description`, optional `model`, and a prompt/body. Cursor says the description is used in Task-tool delegation hints and the body defines the subagent behavior. Citation: [Cursor Subagents](https://cursor.com/docs/subagents).
- A Cursor Agent Skill is a directory containing `SKILL.md`; Cursor discovers skill directories recursively, reads frontmatter metadata (`name`, required `description`, and optional scoping/invocation fields), and surfaces or loads the skill when its description/context matches. Citation: [Cursor Agent Skills](https://cursor.com/docs/skills).
- The two are separate primitives: Cursor's plugin reference describes agents as Markdown behavior/prompt definitions and skills as specialized capabilities in `SKILL.md` directories. A plugin may package both, but the docs do not define a filename/name-based auto-link that makes a custom subagent automatically load a “matching” skill. Therefore, a `reviewer.md` does not implicitly load `skills/reviewer/SKILL.md`; explicit skill invocation/context or a prompt reference is required. Citation: [Cursor Plugins reference](https://cursor.com/docs/reference/plugins), [Cursor Agent Skills](https://cursor.com/docs/skills).
- This separation is consistent with the Agent Skills standard: startup discovery uses only skill `name`/`description`, activation loads the instructions, and referenced resources load as needed. Citation: [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx).

### 2. Skills versus subagents

- Use a skill for reusable expertise, procedures, templates, scripts, and reference material that can be activated in the current agent context; the standard explicitly supports bundled `scripts/`, `references/`, and `assets/`, with progressive disclosure from metadata to instructions to resources. Citation: [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx).
- Use a subagent for an isolated delegated worker with its own role prompt, delegation description, model/tool/permission configuration, and separate task context. Cursor's subagent docs frame custom subagents around specialized knowledge, team standards, and automation. Citation: [Cursor Subagents](https://cursor.com/docs/subagents).
- Anthropic documents the distinction directly: a skill can run in the main conversation or be forked into an agent; a subagent controls its system prompt and may preload named skills. Anthropic recommends skills when the goal is a reusable prompt/workflow in the main context, and subagents when the goal is delegation/isolation; the two can be composed. Citation: [Anthropic: Extend Claude with skills](https://docs.anthropic.com/en/docs/claude-code/skills), [Anthropic: Create custom subagents](https://docs.anthropic.com/en/docs/claude-code/sub-agents).
- “One skill per role” is not a requirement of the Agent Skills standard. It is a design choice. If the skill repeats the entire role prompt and the subagent only points at it, it is duplication; if the skill contains reusable role procedures/resources and the subagent adds isolation, model/tool policy, or delegation semantics, the split is complementary. Citation: [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx), [Anthropic: Create custom subagents](https://docs.anthropic.com/en/docs/claude-code/sub-agents).

### 3. CodeRabbit

- CodeRabbit publicly lists review categories covering Security & Privacy, Stability & Availability, Data Integrity & Integration, Functional Correctness, Performance & Scalability, and Maintainability & Code Quality. Citation: [CodeRabbit review overview](https://docs.coderabbit.ai/guides/code-review-overview).
- Its documented severity levels are Critical, Major, Minor, Trivial, and Info. The docs describe Critical as severe failure/security/data-loss risk and Trivial as low-impact quality suggestions. Citation: [CodeRabbit review overview](https://docs.coderabbit.ai/guides/code-review-overview).
- CodeRabbit says it performs a comprehensive review when a PR is created and incremental reviews when new commits arrive; comments include summaries, security findings, suggestions, and inline/actionable fixes. Citation: [CodeRabbit review overview](https://docs.coderabbit.ai/guides/code-review-overview).
- It can read CI/CD failure output after pipelines produce results and post inline remediation comments for build, unit/integration/end-to-end test, security-scan, IaC, and linter failures. This is explicitly a post-check analysis path, not a claim that the review itself replaces CI. Citation: [CodeRabbit CI/CD pipeline analysis](https://docs.coderabbit.ai/pr-reviews/cicd-pipeline-analysis), [CodeRabbit GitHub Checks](https://docs.coderabbit.ai/tools/github-checks).
- CodeRabbit documents “Learnings-powered reviews”: team feedback/preferences can be saved as learnings and loaded into applicable review context; its CLI also exposes severity summaries and instructions such as fixing critical/major issues while ignoring nits. Citation: [CodeRabbit Learnings](https://docs.coderabbit.ai/knowledge-base/learnings), [CodeRabbit CLI](https://docs.coderabbit.ai/cli).

### 4. Graphite, Copilot, and Bugbot in the PR timeline

- Graphite AI Reviews (the current public docs use “Graphite Agent” rather than relying only on the older “Diamond” name) automatically analyzes new and updated PRs, comments directly on PRs, suggests fixes, focuses on real bugs/context rather than only style, and says it can catch logic issues, edge cases, performance problems, and security vulnerabilities. Citation: [Graphite AI Reviews](https://graphite.dev/docs/ai-reviews), [Graphite setup](https://graphite.dev/docs/diamond-setup).
- Graphite's setup documentation says the Agent works alongside the test suite; its merge documentation says a PR is merged only after approval and GitHub checks/other protections pass, and waits for checks at each stack step. Thus the documented timeline is review feedback during the open PR, with merge after required CI/protections—not “AI review replaces CI.” Citation: [Graphite setup](https://graphite.dev/docs/diamond-setup), [Graphite merge PRs](https://graphite.dev/docs/merge-pull-requests).
- GitHub Copilot code review can be requested on an open or draft PR, or configured automatically on open, draft, or every new push. It reviews changes and suggests fixes, but always leaves a Comment review: it does not count toward required approvals and does not itself block merging. Citation: [GitHub Copilot code review](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/copilot-code-review), [Copilot lifecycle tutorial](https://docs.github.com/en/copilot/tutorials/use-copilot-code-review-across-the-pull-request-lifecycle).
- GitHub's lifecycle guidance recommends draft/early review and re-review before merge after substantial changes; separate rules-based CodeQL/coverage features can provide optional merge gating. Citation: [Copilot lifecycle tutorial](https://docs.github.com/en/copilot/tutorials/use-copilot-code-review-across-the-pull-request-lifecycle), [About Copilot code review](https://docs.github.com/en/copilot/concepts/agents/code-review).
- Cursor Bugbot reviews PR diffs for bugs, security issues, and code-quality problems, posts inline comments with explanations/fix suggestions, runs automatically on each PR update, and can be manually triggered with `cursor review` or `bugbot run`. Cursor also documents that its review can use existing top-level and inline PR comments as context. Citation: [Cursor Bugbot](https://cursor.com/docs/bugbot), [Cursor PR page](https://cursor.com/docs/cursor-review/pr-page).
- Bugbot is therefore an asynchronous PR-review participant during the open-PR lifecycle. Cursor's Azure DevOps integration explicitly says it reviews on open/updates and posts review comments plus a build status; the docs do not state that Bugbot is a required merge approval by itself. Citation: [Cursor Azure DevOps integration](https://cursor.com/docs/integrations/azure-devops), [Cursor Bugbot](https://cursor.com/docs/bugbot).

### 5. Node-based agent builders versus Orchestra's JSON graph

- **LangGraph:** LangGraph provides a runtime/orchestration framework for long-running stateful agents, with explicit nodes/edges, deterministic and LLM-driven steps, conditional paths, loops, durable execution, streaming, and human-in-the-loop. A typed `flow.json` can express a similar control-plane graph (states, routes, transitions, and state fields), but LangGraph additionally supplies executable runtime semantics, persistence/checkpointing, and application integration; JSON alone is a declarative routing specification unless Orchestra supplies an executor. Citation: [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview), [LangChain custom workflows](https://docs.langchain.com/oss/python/langchain/multi-agent/custom-workflow).
- **n8n AI:** n8n is a visual workflow system whose canvas connects trigger/control/data nodes; its AI Agent node chooses among connected tools, and a workflow can be called as another tool. This overlaps with Orchestra's graph as explicit sequencing and branching, but n8n is primarily an executable integration/automation runtime, while Orchestra's typed JSON is a policy/routing contract for named roles, evidence, and terminal states. Citation: [n8n AI Agent](https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.agent), [n8n glossary](https://docs.n8n.io/key-concept-glossary), [Call n8n Workflow Tool](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.toolworkflow).
- **Flowise:** Flowise Agentflow V2 models workflows as granular standalone nodes, including agents, conditions, loops, and flow state shared across nodes; V1 also documents supervisor/worker multi-agent graphs. It is the closest visual analogue to the graph idea, but Flowise provides a node execution UI/runtime and agent communication, whereas Orchestra's JSON emphasizes typed route contracts, role dispatch, approval gates, evidence, and state-machine invariants. Citation: [Flowise Agentflow V2](https://docs.flowiseai.com/using-flowise/agentflowv2), [Flowise multi-agents](https://docs.flowiseai.com/using-flowise/agentflowv1/multi-agents.md).
- **CrewAI Flows:** CrewAI Flows provide structured, event-driven orchestration around crews, tasks, conditionals, loops, branching, and shared state; CrewAI supports both unstructured state and typed Pydantic state, plus persistence. This is conceptually the same class of problem as Orchestra's stateful graph, but CrewAI is an executable Python framework and can run crews/LLM work, while `flow.json` is a portable typed routing/state description whose named roles are dispatched by the orchestrator. Citation: [CrewAI Flows](https://docs.crewai.com/edge/en/concepts/flows), [CrewAI state](https://docs.crewai.com/edge/en/guides/flows/mastering-flow-state), [CrewAI production architecture](https://docs.crewai.com/edge/en/concepts/production-architecture).
- **Bottom line:** They are the same broad abstraction—nodes/roles, edges, state, and control flow—but not the same product/runtime. Orchestra's `flow.json` is best described as a typed, auditable orchestration state machine and routing policy; the cited builders generally combine graph definition with an execution runtime, persistence, integrations, and/or visual tooling. Citations: [Orchestra flow.json](../../.claude/skills/orchestrator/references/flow.json), [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview), [n8n glossary](https://docs.n8n.io/key-concept-glossary), [Flowise Agentflow V2](https://docs.flowiseai.com/using-flowise/agentflowv2), [CrewAI Flows](https://docs.crewai.com/edge/en/concepts/flows).

## Version notes

- Research was performed against public pages available on 2026-08-28. Cursor's model page is explicitly live pricing documentation; prices and model names can change, so the model section expires with this sprint. Citation: [Cursor Models & Pricing](https://cursor.com/docs/models-and-pricing).
- Cursor's public docs distinguish project subagents and skills, while Anthropic's Claude Code docs describe a richer explicit `skills` preload field and `context: fork` behavior. Do not assume Claude Code-specific frontmatter or loading behavior is automatically implemented by Cursor. Citation: [Cursor Subagents](https://cursor.com/docs/subagents), [Anthropic custom subagents](https://docs.anthropic.com/en/docs/claude-code/sub-agents).
- Flowise's Agentflow V1 documentation is marked “Deprecating”; V2 is the current primary architecture in the cited docs. Citation: [Flowise Agentflow V1](https://docs.flowiseai.com/using-flowise/agentflowv1), [Flowise Agentflow V2](https://docs.flowiseai.com/using-flowise/agentflowv2).

## Open questions

- Cursor's public docs do not expose the internal exact system-prompt assembly order for a custom `.cursor/agents/*.md` file versus an activated skill; they document file formats and discovery/activation behavior, not the complete hidden prompt stack. Citation: [Cursor Subagents](https://cursor.com/docs/subagents), [Cursor Agent Skills](https://cursor.com/docs/skills).
- The cited public Graphite pages describe “Graphite Agent” AI Reviews and the `diamond-setup` URL, but do not provide a separate current product specification under the exact name “Diamond.” Treat “Diamond” as a historical/product naming question unless Graphite publishes a dedicated current page. Citation: [Graphite AI Reviews](https://graphite.dev/docs/ai-reviews), [Graphite setup](https://graphite.dev/docs/diamond-setup).
- Public feature pages do not provide a single universal ordering guarantee such as “all AI review vendors always run after CI.” CodeRabbit explicitly documents a CI-failure-analysis path that waits for pipeline results; Graphite and Copilot document review during the open/draft/updated PR lifecycle, with merge protections and CI remaining separate. Citations: [CodeRabbit GitHub Checks](https://docs.coderabbit.ai/tools/github-checks), [Graphite merge PRs](https://graphite.dev/docs/merge-pull-requests), [Copilot lifecycle](https://docs.github.com/en/copilot/tutorials/use-copilot-code-review-across-the-pull-request-lifecycle).
- No cited Cursor public page here establishes prices for “Luna,” “Sol,” “Opus,” “Fable,” or “Kimi” outside the exact model labels and table values recorded above; do not generalize those numbers to renamed/revisioned models. Citation: [Cursor Models & Pricing](https://cursor.com/docs/models-and-pricing), [Cursor Team Pricing](https://cursor.com/docs/account/teams/pricing).
